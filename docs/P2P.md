# MC 游戏 P2P 首版

客户端默认尝试 P2P，4.5 秒内未就绪则继续使用现有 HTTPS/WSS 中继。房主不需要手动配路由器，也不需要安装额外的软件或驱动。联机设置可以选择「仅服务器中继」，该设置保存在客户端，下次自动加入房间时也生效。网页不提供游戏连接操作。

## 链路与边界

- 保留当前本机 TCP 入口和 Forge 1.20.1 开房辅助组件。P2P 成功时，本机 TCP 字节经可靠、有序的 WebRTC DataChannel 传给房主客户端，再连接房主指定的 loopback 游戏端口。
- 同房间每个成员独立协商；允许直连与中继混合。协商信令复用已鉴权 `/bridge/control`，只有房主与本房间的成员可以配对，凭据、成员、会话失效或关房都会关闭相应连接。
- 后台 WebRTC 运行在打包内、沙箱化的本地 WebContentsView，不增加可见窗口。无摄像头、麦克风、文件系统或远程网页权限。每条流采用 16 KiB 帧、512 KiB 接收窗口和发送背压。
- 默认仅配置 `stun:stun.cloudflare.com:3478` 用于地址发现；没有 TURN。STUN 不是游戏数据中继。地址发现不可用、受限 NAT 或 UDP 被阻止时，自动使用现有 WSS 中继，不增加 VPS 公开端口。STUN 可由客户端接入层配置替换。
- 自动模式会向配对的房主/成员交换网络候选，可能包含公网或局域网地址；这些信息不存入数据库、不出现在房间状态及普通成员列表。选择「仅服务器中继」不会发起此交换。
- 房间与游戏库显示当前成员使用的实际连接方式；直连延迟来自 WebRTC 选中候选对的 RTT，尚无测量时不编造数字。房主的「直连 / 中继」统计指客户端会话，不是 MC 在线玩家数；老的 `connections` 仍只统计中继 TCP 通道。
- 直连中断后，现有游戏 TCP 流会关闭。新的游戏连接沿用同一个本机入口走中继，旧字节不跨链路重放。首版不保证游戏中无感切换；可能需要在 MC 中重新连接。
- 新客户端遇到旧服务端、或新服务端遇到旧客户端时，继续使用旧中继。

## 本地验证

`npm run test:p2p` 包含 Node 协议/状态机测试及两个真实 Electron WebRTC 测试，使用内存数据库、临时客户端目录与 MC 协议模拟，不运行真实游戏、不访问线上账号。Electron 测试需要可用的桌面运行环境。

已验证：

- 真实 Chromium 双端 4 MiB 随机数据回显及 SHA-256 校验，慢接收端流控、半关闭、取消和撤销。
- 同一房主下两位真实 P2P 成员与一位强制中继成员并发回显总计 6 MiB；服务端只出现一条游戏数据中继。
- MC 状态查询、故意阻塞协商后的超时回退、直连组件退出后的新连接回退、离房撤销及旧中继兼容。
- 跨房间与角色方向拦截、信令大小限制、包内 IPC 主帧校验以及伪造流量确认拦截。

## Windows 异地验收

需要重新打包客户端，并部署配套服务端信令后再测。两台 Windows 放在不同网络，安装相同房间整合包；房主选择存档开房，成员加入，观察连接方式并实际进入世界。再测试「仅服务器中继」、受限网络下回退、停止联机、离房和重新进入。

本地 loopback 成功不代表所有运营商 NAT 均可直连。Windows 实际游戏、跨网打洞成功率及长时间多人负载尚待验收；本轮未部署服务器或发布安装包。
