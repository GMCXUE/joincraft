# 应用内通知

通知与客户端更新使用独立入口。好友私聊按会话汇总，直接复用服务端聊天未读游标；好友申请、申请通过以及房间整合包更新、游戏环境变更、房间关闭由实际操作产生持久化事件。不发送模拟公告，不将客户端安装包放进消息通知。

`GET /api/notifications` 与 `/api/state.notifications` 提供同一用户的通知摘要、分类数量和最近 100 项。每人保留最近 200 条事件，聊天记录仍遵循原聊天逻辑。WebSocket `state.patch.notifications` 同步新增和已读，离线恢复重新读取完整快照；旧 SSE 客户端继续刷新 `/api/state`。

`POST /api/notifications/read` 可提交通知 ID、通知上界和聊天快照游标。服务端校验归属与好友关系后原子更新，同步聊天侧未读数。全部已读只处理当前快照，新到消息不会被较早的操作吞掉。查看列表本身不会自动已读。

数据库从 v7 升到 v8，新增 `user_notifications` 并迁移现有待处理好友申请，不改账号、房间、存档和聊天记录。部署前使用 SQLite 备份，并准备包含 v8 Store 的旧界面兼容回滚版本；不能用拒绝 v8 数据库的旧程序直接回退。

范围：本轮提供网页与客户端的应用内消息中心，系统消息为真实房间事件。操作系统桌面弹窗、声音和公告后台未启用。

## 界面与验证

右上角提供全部、好友消息、系统消息和已读操作。点击通知进入对应聊天、待处理申请或当前可访问的房间；已关闭房间只保留事件内容，不提供失效跳转。好友私聊汇总只显示实际存在消息的会话，空聊天游标不生成占位通知。游戏库铃铛通过受信任本地 IPC 返回共用消息中心，未读计数只传整数。

本地隔离账户验证了列表分类、单条已读、全部已读、跳转聊天后的游标同步，以及保持页面打开时实时收到新消息。390px 窄屏无横向溢出；macOS 原生客户端验证了房间内消息入口与空状态。测试数据不发布到生产环境。
